# Server security review — 2026-09-16

## Ministry rebuilt and reopened; incident follow-ups remain

`ministryofchemistry.com` contained 13 command-execution plugins (`wp2shell-*`, `admin-utils-*`, `core-helper-*`, `content-tools-*`, `wp-optimizer-*`, `site-tweaks-*`). Their PHP exposes unauthenticated REST command execution and token-protected direct shells, plus credential reconnaissance. File timestamps run from July 23 to September 3. Retained access logs contain HTTP 200 responses from `loot.php` and `direct.php` on September 2–3. Response bodies were not retained; the exact data accessed is not established.

The exact verified directories were moved out of the web root into `/root/wordpress-quarantine-2026-09-16-4l1564a2`. SHA-256 hashes, sizes, timestamps and original paths are recorded in `manifest.json`. A subsequent check also found nine unauthorized PHP files inside Ministry's core directories. The whole old webroot is now root-only at `/root/wordpress-rotation-2026-09-16-qirv72ul/old-ministry-webroot`. None of this old executable code is used by the rebuilt site. Historical plugin paths and REST namespaces are denied by Nginx. Original evidence is retained, not erased.

Ministry was taken completely offline during recovery, including static files. Its WordPress core was rebuilt at 7.1 from the official distribution; nine retained/replacement plugins and Twenty Twenty-One were installed from official packages. Every standard core/plugin checksum and every theme file passed verification. Thumbs Rating could not be obtained through official plugin metadata (HTTP 404), so it was not carried forward. This removes the small voting feature rather than trusting the old PHP.

The database and static media were retained after targeted inspection. 1,936 PNG/JPEG/GIF/WebP files were copied, while six non-media files were retained only in quarantine. Thirty corroborated attack/test database records were privately exported and removed; genuine articles/pages/attachments were preserved. Fourteen confirmed shell-created administrators were deprivileged. The incident-era `cherise-leming38` account is unverified, not assumed malicious, but is suspended and has no administrator role. Only Simon remains a Ministry administrator. All Ministry account passwords were reset, all sessions/application passwords were revoked, and Simon now requires a newly enrolled TOTP authenticator.

Acceptance checked all 98 published articles/pages, 24 homepage media/theme resources, correct 404s and denied configuration/shell URLs. An actual password login was verified to require TOTP; password-plus-TOTP opened the admin dashboard, and the test session was revoked. Ministry was reopened only after these checks. The public homepage, blog and login page were also verified in a normal browser through Cloudflare, with homepage images loaded. The VM's automated public requests encounter Cloudflare's bot challenge; this is separate from the tested application runtime.

Both WordPress sites formerly shared `www-data`, so Molecule Store database/API/two-factor secrets may also have been readable. They now have separate PHP identities and sockets (`wp-ministry`, `wp-molecule`), mode 0640 root-owned configurations readable only by the respective application group, and OPcache permission validation. Store's Redis cache now uses authenticated, namespace-restricted ACL access: anonymous access, cross-namespace reads, configuration commands and global flush are denied. Its Redis plugin/drop-in was replaced from official source and caching remains enabled. Production debugging is disabled and the previously public debug log was privately quarantined.

Both database passwords and WordPress authentication constants were rotated. Store's `simon` and `office` passwords were reset; customers' passwords were not changed. All Store sessions, application passwords, old backup codes and MCP JWT secrets were invalidated; existing TOTP enrollments were preserved. `simon` is the sole network superadministrator and has TOTP configured. The owner confirmed that `office` belongs to Sol; it is a shop manager on the English/German sites and still has **no two-factor enrollment** (user ID 203, no stored TOTP seed at recheck). Ownership confirmation does not clear the enrollment follow-up. A separate customer account matching Sol's name is not privileged and was left unchanged. Share only Sol's individual `office` password through a secure channel, never the whole private recovery file containing other administrator passwords and Ministry authenticator details. Sol must enroll his own authenticator. Re-enroll Store privileged 2FA if treating the old seed as exposed.

The old WooCommerce Printful/Printify keys (IDs 1 and 2, last used February 2026 and April 2022) were privately backed up and retired. The currently used Printful key (ID 3, used today) was preserved to avoid interrupting fulfillment; revoke/reconnect it through the provider as a follow-up. Other potentially exposed payment, fulfillment, mailing and media API credentials still need provider-side revocation/reconnection. The Telegram token was previously too readable and is now root-only; its rotation is explicitly deferred at the owner's request. Do not regard existing server backups as clean executable recovery sources.

The attempted AIDE initialization was stopped before a reference database was accepted. AIDE's missing baseline remains an explicit monitoring issue. Create the baseline only after trusted remediation; do not accept the infected installation as the reference state.

This is a verified application rebuild and credential cleanup, not complete host forensic clearance or a claim that no customer data was accessed. The subsequent full `dpkg --verify` check found zero non-configuration file mismatches and five expected configuration differences. Persistence, SUID/capability, account, SSH-key and running-executable inventories found no extra UID-0 account or unusual running executable. Package-manager references are not independent forensic proof. A provider snapshot/clean-host migration, remaining Store licensed-plugin verification, external credential revocation and an off-server backup/restore test remain advisable. AIDE's reference baseline must only be accepted after the remaining integrity review.

A newer vendor release should undergo full lint and staging acceptance again.

A private loopback-only, separate-UID/network-namespace Store clone verified English/German gateways, unchanged credential mapping, Stripe availability, ordinary cart/checkout rendering, REST embedding and configuration denials. Outbound HTTP, mail, cron and TCP networking were blocked. The update used an atomic plugin-directory exchange, a brief normal maintenance flag and FPM reload, followed by live gateway/home/cart/login checks and unchanged-setting verification. No payment or order was submitted. Actual provider revocation/reconnection, completed transactions and webhook/fulfillment testing remain follow-ups requiring provider access. Temporary staging services/configurations were retired; the webroot is root-only and its database account is locked, with no remaining staging connections.

Prior direct maintenance access for `simxn` is retained with named ACLs. `open_basedir`, dedicated private upload/temp storage and disabled command-execution functions constrain this pool. Cross-application configuration/key reads were tested and denied. The unused generic `www-data` PHP pool was recoverably retired.
- All four foildata image-upload paths validate actual image content/MIME, dimensions and size, and use random canonical names to prevent replacement of existing images. Previously the brand/parawing forms could upload arbitrary executable files. Uploaded PHP-like files are denied before PHP routing; no such existing files were found in the image tree. Duplicate submission scripts and a null template-price-input error were removed; duplicate in-flight submits are blocked. Fourteen client assertions passed. - Foildata voter-IP tracking JSON files are denied to HTTP while remaining available to their PHP handlers. Normal public map/product JSON remains available. Community endpoints remain intentionally anonymous as before; this is not an authentication/moderation redesign or a complete stored-content/concurrent-write audit.
- Nginx now trusts `CF-Connecting-IP` only from the 15 IPv4 and seven IPv6 ranges in Cloudflare's official public API, verified today. Private trusted/untrusted proxy tests passed, including rejection of spoofed headers from untrusted callers. Review the range list regularly; the existing UFW allowlist was not changed. See [Cloudflare's visitor-IP guidance](https://developers.cloudflare.com/support/troubleshooting/restoring-visitor-ips/restoring-original-visitor-ips/).
